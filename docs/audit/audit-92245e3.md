### 1. G1 大区域上的落脚面积检查塌缩：栅格步长抽样让容差看不到行间隙（grasp）
- **位置**：`services/pi_embodied_services/utils/grasp.py:1697`（`region_xy = region_w[:: max(1, len(region_w) // 3000), :2]`），`_landing` 1820–1847。提交 20944b0ac。
- **原因**：区域点云按光栅顺序（行主序）隔 k 个取一个。抽出来的点沿行相隔 k 像素，但纵向只隔约 1 行，所以 `_landing` 用最近邻估出的 `spacing` 只看到几像素的纵向间隙，容差 `max(0.015, 1.5*spacing)` 停在 1.5–2 cm，而物体点真正要跨的行内间隙是 k/2 像素、几厘米。大部分物体点被判成"不在区域上"。
- **后果**：区域一大（桌面、台面、Franka 640×480 相机下的大托盘）就整批拒绝。数值复现：60×60 px 物体落在 80×80 区域 → footprint 1.00；200×200 区域（步长 13）→ 1.00；300×400 区域（12 万点、步长 40）→ **0.27 < 0.8**，每个 AnyPlace 候选都报"only 27% of the object's footprint would be over the region (its edge)"，`plan_place` 抛"none of AnyPlace's N placements can be executed"。仓库测试只用 16×16 帧（test_grasp.py:187）和 200×210 px 的盘子（test_libero_code.py:541），都在步长咬人的阈值以下。未上机验证。
- **修法**：各向同性地抽样（xy 栅格/体素降采样，或 `rng.choice` 随机子集），`spacing` 从深度图在该深度的像素间距（fx/z）推，不要从抽稀后的最近邻估；或者把区域栅格化成 xy 占用图直接查。
- **证据**：三票皆真（refute 0.92 / reproduce 0.92 / severity 中 0.90）。
- **状态**：**仍在**（grasp.py 在 92245e333 之后没有改动；1697 / 1729 / 1847 行原样）。

### 5. CM-3 隔离豁免相信客户端的 `remote` 标志；同机 pi 用 FQDN / 局域网 / tailnet 地址就被判成远程（code-mode）
- **位置**：`packages/embodied/src/modes/code/index.ts:156–160`（`isLocalEndpoint`）、`:538–543`；`services/pi_embodied_services/utils/code_exec.py:1148–1156`（`preflight`）、`:1193`。提交 5b465f4fe。并入 S1（safety）、C4（consistency）。
- **原因**：`CodeRunner.preflight(remote=True)` 置 `isolation_waived = True`，此后 `code.run` 整个服务生命期都跳过 `code_isolation_error()`；而 `remote` 完全由客户端算：`isLocalEndpoint()` 只认回环字面量和 `os.hostname()` 的**大小写敏感**精确匹配。WHATWG URL 会把 hostname 小写，`os.hostname()` 保留大小写（本机实测 `BorisGuodeMacBook-Pro.local` ≠ `borisguodemacbook-pro.local`）；本机的 192.168.x.x / 100.64.x.x 永远不等于 hostname。服务端拿得到对端地址（`http_rpc.py` 的 `BaseHTTPRequestHandler.client_address`）却不用。豁免还是**粘住的**：之后不走 preflight 的调用者（老 pi、拿 token 直连 RPC、替身）也跑在非隔离状态（S1）。
- **后果**：机器人 PC 上非 root env server 监听 0.0.0.0:9000，操作员在同一台机上 `--robot-env http://robot-pc.local:9000#tok`（或 192.168 地址）→ 判远程 → 豁免 → 模型程序以 pi 的 uid 在 pi 的主机上非隔离运行，`open('/proc/<pi pid>/environ')` 读走 ANTHROPIC/OPENAI key——这正是 `code_isolation_error` 要挡的事。PROTOCOL.md 写的"caller on another host"没有任何服务端校验（C4）。
- **修法**：远程与否在服务端判（对端地址不是回环、也不是本机任一接口地址才豁免，或要求服务端显式 `PI_EMBODIED_CODE_REMOTE_OK=1`），忽略或交叉核对客户端布尔；每次调用判一次，不要锁存。客户端至少 hostname 比较忽略大小写，并把 `os.networkInterfaces()` 里的地址都算本机。
- **证据**：三票皆真（severity 中 0.85 / refute 0.85 / reproduce 高 0.90）。现有测试 code.test.ts:638–639 只测 127.0.0.1 与 `robot-pc.tailnet`，没有"同机 IP"用例。
- **状态**：**仍在**（code/index.ts 的三个后续提交没碰 `isLocalEndpoint`；code_exec.py 只有 e777d572 改了 done 消息）。

### 6. HC-1 eval.sh 每个 episode 取 LOCK，而 eval-parallel 已经持有它：必死锁（humanclaw）
- **位置**：`packages/embodied/src/robots/humanclaw/eval.sh:82`（`${LOCK:+flock "$LOCK"} $PI ...`）；`packages/embodied/src/scripts/eval-parallel.sh:217–222`（fd 9 独占 flock）、`:255`（`env $envs bash "$script" ...`，没有 `-u LOCK`）、`:292`（`worker "$k" 9>&-`）。提交 409298b9f。
- **原因**：eval-parallel 对 heavy 机器人（现在含 humanclaw）在启动 worker 前拿一次独占锁、全程持有，worker 用 `9>&-` 关掉 fd 但 **没有从环境里清掉 LOCK**。子进程 eval.sh 于是 `flock /path/gpu.lock pi ...`，重新打开锁文件、等父进程放锁；父进程要等所有 worker 退出才放。其他机器人的 eval.sh 都不自己用 LOCK，只有 HumanCLAW 这条。两个脚本的头注释互相矛盾（eval-parallel.sh:45–47 "workers ... do not hold it"；humanclaw/eval.sh:15–16 "each episode takes it with flock"）。
- **后果**：`LOCK=/root/autodl-tmp/locks/gpu1.lock eval-parallel.sh -j 1 --gpus 1 humanclaw runs/hc val100 --mode paper ...` → 一个 episode 都起不来，永不结束，排在这把锁后面的任何作业一起挂。
- **修法**：eval-parallel 对 humanclaw 用 `env -u LOCK` 起 eval.sh（或一个 `EVAL_PARALLEL_HOLDS_LOCK` 守卫），或者从 eval.sh 里删掉逐 episode 的 flock、像其他 heavy 机器人一样只靠 eval-parallel 那把锁。
- **证据**：三票皆真（severity 中 0.90 / reproduce 高 0.95 / refute 高 0.93）。
- **状态**：**仍在**（3a4baf4c 改了 humanclaw/eval.sh 但 82 行原样；422394b2 改了 eval-parallel.sh 但 worker 仍 `env $envs bash`）。
